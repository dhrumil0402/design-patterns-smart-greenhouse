## A. Pattern

1. State the intent of Abstract Factory in plain language. What goes wrong when related products are chosen independently (`if format` for each piece) instead of as a **family**?

Abstract Factory is about creating a whole group of related objects together, through one factory, so that everything you get back is guaranteed to belong to the same family. The problem with choosing each piece independently is that nothing stops the pieces from ending up mismatched. If I picked a sensor type with one `if` check and an actuator type with a completely separate `if` check, someone could accidentally end up with a simulation sensor paired next to an edge actuator, and there'd be no single place in the code that would catch that. It would still "work" in the sense that nothing crashes, but it would be inconsistent in a way that's confusing to debug later, since the two devices wouldn't share the same protocol or config style.

2. Name the main participants (**abstract factory**, **concrete factory**, **abstract products**, **concrete products**, **client**). How does choosing a factory at the start **commit** the client to one family?

In this lab, `DeviceFamilyFactory` is the abstract factory, and `SimulationDeviceFactory` and `EdgeHardwareFactory` are the concrete factories. `Device` acts as the abstract product, since both sensors and actuators are represented by the same entity rather than having separate product classes per role. The client is `DeviceFamilyService`, which never constructs a concrete factory by name, it goes through `get_family_factory(family)` instead. Choosing a factory commits you to a family because once you call `get_family_factory("edge")`, every device that comes back from `create_device_set()` on that factory is tagged with `device_family="edge"`, there's no way to mix in a simulation device from that same call, so the whole kit stays consistent by construction.

3. When should you use Abstract Factory, and when should you skip it (for example only one product type per request, or mixing siblings is valid)?

I'd use it when I actually need a matching set of things that have to stay consistent with each other, like sensors and actuators that all need to agree on the same protocol. I'd skip it if I only ever needed to create one product per request, since then Factory Method alone would already be enough and Abstract Factory would just be extra structure for no real benefit. I'd also skip it if mixing siblings was actually fine for the use case, since the whole point of the pattern is preventing mixing, so if that constraint doesn't matter, the pattern doesn't add anything.

## B. This phase of the application

4. In this lab, what is a **device family**, and what does `create_device_set()` (or your equivalent) return? Why must a simulation kit and an edge kit not mix incompatible siblings?

A device family in this lab is basically a named, coherent group of devices that all share the same style of configuration, right now that's either `simulation` or `edge`. `create_device_set()` returns a list of four `Device` objects for whichever family you called it on, two sensors and two actuators, all tagged with that same family. A simulation kit and an edge kit can't mix because they're meant to represent two different environments, simulation devices use `protocol: sim` while edge devices use `protocol: gpio-stub`, and if those got mixed on the dashboard it would be genuinely confusing to tell which devices are meant to represent real stub hardware and which are just for local testing.

5. Phase 2 Factory Method creators still exist. How does Abstract Factory **compose** them rather than replace them? What would you lose if you deleted the sensor creators and inlined all construction inside the family factory?

Inside `SimulationDeviceFactory.create_device_set()`, I call `MoistureSensorCreator().create_sensor(...)` and `LightSensorCreator().create_sensor(...)` just like Phase 2 did, and then I wrap the resulting `Sensor` into a `Device` with the family tag added. So the family factory doesn't reimplement sensor defaults, it just reuses the creators that already exist and adds the family and actuator pieces on top. If I deleted the sensor creators and inlined everything into the family factory instead, I'd lose that single source of truth for sensor defaults, both `SimulationDeviceFactory` and `EdgeHardwareFactory` would each need their own copy of the moisture and light sensor logic, and any future change to those defaults would have to be made in two places instead of one, which is exactly the kind of duplication Factory Method was there to prevent in the first place.

6. Why add a `device_family` column on the existing `devices` table (with a default/backfill such as `"simulation"`) instead of a new table per family? What happens to Phase 2 sensor rows if you forget the backfill?

Adding a column keeps sensors and actuators from every family in one table, which fits how the rest of the app queries devices, by role and now by family, without needing to know which table to look in first. A separate table per family would mean duplicating the whole `devices` schema for each new family and writing separate queries every time, which doesn't scale well if a third family gets added later. If I forgot the backfill, my Phase 2 sensor rows would end up with `device_family` as `NULL` instead of `simulation`, which would either break anything that expects the field to always have a value, or just silently disappear from any filtered list that expects a real family string. Using `server_default="simulation"` on the column meant Postgres backfilled the existing rows automatically the moment the migration ran, so I didn't have to write a manual `UPDATE` for it.

7. `POST /api/devices/provision` returns a kit (expected size: two sensors and two actuators). `GET /api/devices` can filter by `family` and `role`. Why must the UI be able to filter by family? Why do `/api/sensors` routes from Phase 2 still need to work?

The UI needs to filter by family so an operator looking at the dashboard can actually tell which devices belong to which environment, without the filter, the simulation and edge lists would just blend together and you'd lose the whole point of having families in the first place. The `/api/sensors` routes from Phase 2 still need to work because they're role-scoped rather than family-scoped, they were built to list anything with `role="sensor"` regardless of family, and other parts of the app, or anyone still using that endpoint, shouldn't break just because Phase 3 introduced a new concept on top of the same table.

## C. Compare, contrast, and scenarios

8. Draw the contrast in one paragraph: Factory Method vs Abstract Factory. Use the questions "which **one** product?" versus "which product **line**?" and mention that Abstract Factory often **uses** Factory Method–style methods inside.

Factory Method answers "which one product should I build right now," like choosing between a moisture sensor and a light sensor. Abstract Factory answers a bigger question, "which whole product line should I build," like choosing between a simulation kit and an edge kit, where each kit itself is a bundle of multiple products. In this lab that relationship shows up directly, `SimulationDeviceFactory` and `EdgeHardwareFactory` are both Abstract Factory implementations, but internally they still call the Phase 2 Factory Method creators to decide which specific sensor to build, so Abstract Factory sits a level above Factory Method rather than replacing it.

9. A DTO or HTTP handler constructs concrete simulation/edge device types directly, bypassing the family factory. What consistency bug can that reintroduce? How should HTTP stay on the abstract factory / service instead?

If a DTO or handler constructed devices directly instead of going through the factory, you'd reintroduce the exact bug Abstract Factory is meant to prevent, two different code paths could end up disagreeing on what a family's defaults should look like, like one place using `protocol: sim` and another accidentally using a different string or forgetting the field entirely. That kind of drift would be hard to catch since nothing would technically be wrong syntax-wise, it would just be quietly inconsistent. HTTP should stay on `DeviceFamilyService`, which is the only thing that's allowed to call `get_family_factory`, so there's exactly one place responsible for deciding what a family's devices look like.

10. Someone proposes a single "god factory" that creates locations, readings, and devices "because we already have a factory." Why is that a misuse of Abstract Factory?

That would be a misuse because those things aren't actually a family that needs to stay consistent with each other, a location, a sensor reading, and a device don't need to be created together or share any kind of matching configuration the way a sensor and an actuator in the same kit do. Abstract Factory is meant for products that genuinely belong together as a set, not just anything that happens to involve object creation. Locations have their own construction concerns that fit Builder instead, readings are just persisted data with no family concept at all, and cramming all of that into one factory would turn it into a dumping ground rather than something that's actually enforcing a real consistency rule.
